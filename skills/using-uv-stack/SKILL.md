# Using uv-stack

## Overview

The `stack` CLI manages Python environments declaratively: micromamba owns
the interpreter and conda-level binaries; uv owns pip packages, compiled to
a pinned lock. Define packages once in profiles (package lists) and bundles
(groups of profiles); install those definitions into shared environments or
uv projects.

**Core principle: change source files, then re-render. Never mutate a
managed environment or a generated file directly.**

## First: probe and orient

1. **Probe:** `command -v stack`. If absent, stop — the rest of this skill
   does not apply; use plain uv/micromamba and offer
   `uv tool install uv-stack`.
2. **Config root:** `$UV_STACK_ROOT`, else legacy `$UV_ENV_ROOT`, else
   `~/.config/python-envs`.
3. **Machine policy:** read `<config-root>/AGENTS.md` if it exists — it
   overrides this skill's generic guidance.
4. **Discover with the CLI** (each takes `--json`), not filesystem
   forensics:

```bash
stack list env            # also: profile, bundle
stack show env NAME       # tokens, python, resolved packages
stack status              # per-env: exists? lock present? sources/Python changed?
stack doctor              # config problems + suggested fixes
stack show project        # tracked project in CURRENT directory
```

## Staleness: a two-step check

`stack status` compares sources to rendered files, checks lock freshness, and
probes each env's live interpreter — but never installed packages (build-time
`uv pip check` covers pip sync). Answering "is anything out of sync?" takes
both steps:

1. `stack status` for source/lock drift and interpreter drift (state
   `python changed`, Python column `3.12 (env 3.14)`); `stack doctor` for
   layout.
2. Conda packages (status's remaining blind spot): `micromamba.txt` and
   `channels.txt` apply only at env (re)creation — `stack upgrade` re-syncs
   the pip layer only. If either changed after the env was built (creation
   date: `conda-meta/history`), compare `micromamba list -n NAME` with
   `environment.yml`; only conda-channel rows count (`pypi` rows never
   satisfy it), and a newer mtime alone is not drift. Fix drift with
   `stack create env NAME --recreate`.

## Task → action

| Task | Action |
| --- | --- |
| Add/remove package in shared env | Edit a profile it uses (machine-local: `envs/NAME/requirements.local.in`), then `stack upgrade NAME --no-upgrade` |
| Float pins to newest versions | `stack upgrade NAME` (`--upgrade-package PKG` for just one) |
| New shared env | `stack create env NAME TOKENS... --python 3.12` |
| Change an existing env's Python | `stack create env NAME --python 3.14 --recreate` (plain version only; a match spec like `3.12.*` is refused) |
| New project | `cd <dir>`, then `stack create project TOKENS...` — never hand-roll `uv init` + `uv add` |
| Push profile changes to a tracked project | `stack refresh` from the project root (`--dry-run` shows the delta) |
| Add tokens to a tracked project | `stack sync project TOKENS...` from the project root — appends to the recorded stack, never replaces it |
| Remove a profile or bundle | `stack delete profile\|bundle NAME` (`-y` skips the prompt). Refused while an env's `stack.txt` or another bundle still refers to it, and the refusal names each place: edit those references out, then delete. `--force` is not a shortcut — it leaves a bare token that now means the pip package of that name |
| Remove a shared env | `stack delete env NAME` — removes the micromamba env if it was built, then `envs/NAME/`. Not `rm -rf envs/NAME` or `micromamba env remove`: either alone orphans the other half |
| Stop managing a project with uv-stack (hand it off as a plain uv project, untrack it) | `stack delete project` from the project root — `uv remove`s the packages uv-stack applied and drops `[tool.uv-stack]`; your own dependencies, `pyproject.toml`, `uv.lock`, and `.venv` stay. Deleting the table by hand leaves uv-stack's packages behind as nobody's; `uv add` back any the project needs on its own |
| Build every env on a fresh clone, or bring a whole root up to date | `stack doctor` first (names declared variables with no value here), then `stack sync` — creates missing envs, keeps existing pins; `stack sync env NAME...` for some |
| How do two envs differ, here or on another machine? | `stack diff A B`; a source is an env name, a lock file, or the path to another machine's `envs/NAME/` dir wherever it sits. It reads declared config and compiled pins, never what is installed: same pins but different behavior points at installed state (the staleness check) |
| Put envs on another machine over ssh | `stack sync remote ITEMS DEST` (`env:ml`, `profile:X`, `@B`, or a bare name; none = whole root; `--dry-run` first): exports here, imports and builds there, with the profiles and bundles the items use. It reads DEST's stack command and root from `remotes.yaml` and explains ssh's exit codes |
| Bring envs here from another machine | `ssh HOST stack export ITEMS \| stack import -` (or `export -o FILE` there, `stack import FILE` here). The document carries what the items use plus each env's lock, whose pins seed this machine's compile |
| Import refused: a file differs | Read the printed diff. To take the incoming version: `stack import FILE --overwrite --dry-run`, then without `--dry-run`. `--overwrite` also removes env files the source no longer has. A dry run without `--overwrite` stops at the same refusal |
| Remote's `stack` not found over ssh, or its root is not the default | `stack config remote set HOST --stack 'PATH=$HOME/.local/bin:$PATH stack' --root /abs/path`. Single quotes keep `$HOME` for the remote shell; a full path to `stack` is not enough, because the import runs `uv` from PATH too. HOST must match DEST as typed. A `remotes.yaml` with comments: `stack edit remotes`, since `set`/`remove` refuse to drop them |
| A path differs per machine (editable checkout) | Declare `NAME` in `variables.txt`, write `${NAME}` in the profile, set each machine's value in `variables.local.txt` |
| Put the config root in git | `stack config portable`, then run the git commands it prints (it never runs git) |
| User wants to edit a config file themselves | `stack edit profile\|bundle\|env\|project\|remotes [NAME]` — validates when the editor exits; GUI editors need their blocking flag: `--editor 'code -w'` |
| Which envs exist / stale? | The two-step staleness check above |
| What does token X mean? | `stack resolve TOKENS...` (`--full` expands to packages) |

Preview any mutation with `--dry-run` (`stack delete` has none; its prompt
states what goes). Tokens: a bare name resolves
profile → bundle → literal package; force with `profile:`, `@`/`bundle:`,
`pkg:`; `--strict` errors on unqualified fallthrough.

## Hard rules

- **Never edit generated files** (`requirements.in`, `environment.yml`,
  `requirements.lock.txt`). Edit `stack.txt`, `requirements.local.in`,
  `profiles/*.yaml`, `bundles/*.yaml` instead.
- **Never install directly into a managed env** (`pip install`,
  `uv pip install`, `micromamba install`): the next upgrade syncs exactly
  to the lock and removes untracked additions.
- **Managed = has `envs/<name>/stack.txt` under the config root.** Leave
  other micromamba envs to their owners; `stack delete env` refuses them.
- **No project registry, no parent-directory search:** run `stack refresh`
  / `stack show project` from the `pyproject.toml` directory. No
  `[tool.uv-stack]` table means a plain uv project — use normal `uv`
  commands.
- **Project interpreter default:** `$UV_STACK_PROJECT_PYTHON`, then
  `<config-root>/project-python.txt`, then 3.12 — don't invent one.
  `--python <env-name>` builds on that micromamba env's interpreter.

## Common mistakes

| Mistake | Reality |
| --- | --- |
| Hand-editing `requirements.in` / running `uv pip compile` yourself | Pre-uv-stack flow; `stack upgrade` renders, compiles, syncs, checks. |
| `uv init` + `uv add` for a new project | Skips profiles, tracking, and the configured interpreter. Use `stack create project`. |
| Re-pinning a stack-applied package via `uv add` | stack still owns the name; a later refresh may rewrite it. Pin in the profile. |
| Diffing lock vs `pip freeze` for staleness | Use the two-step check; deep-diff only for a suspected sync failure. |
| `stack upgrade` to move an env to a new Python | Upgrade re-syncs the pip layer only, and refuses outright once the live interpreter stops matching `python.txt`. Retarget with `stack create env NAME --python X.Y --recreate`. |
| Treating `pending` in `[tool.uv-stack]` as corruption | Interrupted-run marker; the next `stack refresh` (or tracked create with `--force`) cleans it up. |
| `stack upgrade --all` or a `create env` loop on a fresh clone | Upgrade never creates a missing env. `stack sync` does. |
| Hand-diffing another machine's files, or copying its lock, profiles, or `envs/NAME/` into this root (or scp to one) | `stack diff` reads their dir in place. To bring their env here, `stack import` their export; to send yours, `stack sync remote`. Locks are per-machine output: to match one version, pin it in a profile or `requirements.local.in`, then `stack upgrade NAME --no-upgrade`. |
| A second profile or per-machine `requirements.local.in` for a path that differs | Use a variable; `stack doctor` then names every machine missing a value. |
| Hand-writing the root's `.gitignore` | `stack config portable` knows what is machine-local: `variables.local.txt`, `editor.txt`, `requirements.local.in`, and compiled locks stay out. |
| `rm profiles/X.yaml`, `rm -rf envs/X`, `micromamba env remove`, or hand-deleting `[tool.uv-stack]` to get rid of something | `stack delete` checks what still refers to a profile or bundle, removes an env's conda layer and sources together, and withdraws a project's applied packages along with its table. Hand removal skips all three. |
